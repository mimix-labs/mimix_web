# MediaProvider / LiveKit (phase 4, prompt 16)

## Deployment and boundary

Feature is **off by default**. This phase supplies the media contract, backend
control plane and executable WebRTC harness. It models robot camera, microphone
and speaker; it does not install a robot SDK, access physical devices, or add UI.
The separate `mimix_robot` repository is unchanged.

Browser and robot send media directly to LiveKit using WebRTC. API HTTPS handles
pairing, room provisioning and scoped admission credentials. LiveKit's WSS
connection carries its own signaling, never a Mimix generic WebSocket video stream.
LiveKit credentials belong only in the backend. The robot receives a Device token
and its own room JWT, never a Clerk JWT or the provider API secret.

Apply `0005_media-sessions.sql` through `pnpm --filter @mimix/api db:migrate` before
enabling. This adds `media_sessions`, foreign keys and indexes, including one open
room per DeviceSession. Existing data is unchanged. The runtime database role needs
SELECT/INSERT/UPDATE on `media_sessions` and the existing DeviceSession permissions.
Use a separate migration role, as in the PostgreSQL and device runbooks.

Required environment, in addition to the existing Clerk/PostgreSQL/DeviceSession
configuration and shared `MIMIX_DEVICE_TOKEN_KEY`:

```dotenv
MIMIX_MEDIA_PROVIDER=livekit
MIMIX_LIVEKIT_MODE=cloud
LIVEKIT_URL=wss://your-project.livekit.cloud
LIVEKIT_API_KEY=<server-only key>
LIVEKIT_API_SECRET=<server-only secret of at least 32 characters>
MIMIX_MEDIA_LAN=false
```

For self-hosted infrastructure set `MIMIX_LIVEKIT_MODE=self-hosted`. Use WSS behind
TLS. Cleartext WS is accepted only with `MIMIX_MEDIA_LAN=true` and a literal private
or loopback IP. The API must reach the room-service endpoint; participants also
need ICE connectivity. Configure UDP media, TCP fallback and TURN according to the
[LiveKit ports guide](https://docs.livekit.io/transport/self-hosting/ports-firewall/).
An HTTP-only reverse proxy is insufficient. Never expose the development test
configuration to the Internet. Keep backend/database/provider clocks synchronized.

## Permissions and HTTP

Robot capability announcement accepts optional `audio: {microphone, speaker}`.
Absent audio grants nothing. `speech: true` alone grants neither microphone capture
nor speaker subscription. The user explicitly approves capabilities at pairing.

| Selected track | Pairing capability | Robot participant | User participant |
| --- | --- | --- | --- |
| `robot_camera` | `camera:webrtc` | publish camera | subscribe |
| `robot_microphone` | `microphone:publish` | publish microphone | subscribe |
| `robot_speaker` | `speaker:subscribe` | subscribe | publish microphone |

Rooms and identities are generated by the server, with at most two participants.
No data publication, screen sharing, recording, room administration or metadata
updates are granted. LiveKit's source permission classifies track sources; it cannot
prove which physical sensor produced the media. Trusted device implementations must
bind those sources to the approved hardware.

All endpoints are no-store and use the shared origin and quota policy:

| Method and path | Credential | Request / result |
| --- | --- | --- |
| POST `/api/media/sessions` | originating user Bearer | `{schemaVersion:1, deviceSessionId, tracks}` |
| GET `/api/media/sessions` | owner Bearer | 50-item page, optional `after` cursor |
| GET `/api/media/sessions/:id` | owner Bearer | state and current lease |
| DELETE `/api/media/sessions/:id` | owner Bearer, including new login | close; 202 if remote cleanup pending |
| POST `/api/media/sessions/:id/user-token` | originating user Bearer | `{schemaVersion:1}` |
| POST `/api/media/sessions/:id/device-token` | paired Device | `{schemaVersion:1}` |
| POST `/api/media/sessions/:id/disconnect` | paired Device | `{schemaVersion:1}` |

Create returns 201 with `{status:"ready", session, connection}`. Token requests
return that shape with 200. `connection` includes URL, generated room/identity, JWT,
expiry, directional permissions and `revocation` (`provider-managed` or
`best-effort`). Provider failure returns 200 `{status:"degraded", session,
reason:"PROVIDER_UNAVAILABLE", fallback}` without any JWT. Unknown request fields,
including caller-selected room, identity or role, are rejected. OpenAPI mirrors
Nest and temporary Express routes. Feature-off routes and schemas are hidden.

## Lifecycle, failure and revocation

Media lifetime is at most five minutes, bounded by DeviceSession absolute expiry.
Admission JWTs last at most 30 seconds and never beyond current presence/device/media
expiry. Issuance rechecks PostgreSQL, original Clerk session and approved device
grants while holding the same owner/device locks as revoke. A durable room intent
commits before any provider side effect, so a crash during provision leaves work
that can be cleaned. A provider delay past the device lease returns no credential.

Clients must use `mediaOutputPolicy`, arm a deadline watchdog, and stop capture and
playback on connecting/disconnected/degraded state or `leaseExpiresAt`. Poll owned
session state to obtain a renewed lease after successful device heartbeats; never
extend a lease locally from JWT refreshes. Release media tracks and hardware when
stopping. Browser/robot production consumers remain a follow-up integration.

Close, device revoke/disconnect/presence expiry and media expiry move the database
state to `closing`; successful remote removal/deletion changes it to `closed`.
A five-second worker retries pending cleanup, at most 100 rows per batch with
concurrency eight and a rotating UUID cursor, so persistent failures do not starve
later rooms. Provider RPC timeout is three seconds per call. Five seconds is a poll
interval, not a worst-case revocation SLA under backlog or outage. New tokens are
fenced immediately by authoritative state. Inspect `closing` counts/age, API errors
and provider reachability operationally; never log JWTs or provider response bodies.

API replica restarts resume durable pending work. Healthy rooms survive a replica
restart until their existing leases end; starting a replica does not close all
other replicas' valid rooms. Complete API/database outage prevents backend cleanup;
trusted consumers must still enforce their existing lease deadline. An adversarial
consumer cannot be forcibly disconnected while the provider control plane is down.

**JWT expiry limits admission, not an already connected participant.** LiveKit
refreshes participant tokens. Cloud removal uses an explicit revocation timestamp
for both generated identities followed by room deletion. This avoids the default
one-minute cutoff tolerance. Actual Cloud tenant revocation has not been exercised
here; the SDK RPC payload is covered. Self-hosted removal/deletion disconnects
current participants but cannot invalidate cached/refreshed JWTs: they may rejoin or
recreate the room. Therefore self-hosted mode is explicitly `best-effort`, not strict
revocation. See [tokens/grants](https://docs.livekit.io/frontends/reference/tokens-grants/)
and [participant removal](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/).

## Temporary MJPEG LAN fallback

`MIMIX_MEDIA_LAN=true` also requires `MIMIX_VISION_VIDEO_URL` to use a literal private
or loopback address. When a requested camera session fails and pairing approved
`camera:mjpeg`, only the user response includes the fixed `/api/vision/video`
descriptor. The existing operator credential remains required. Media JWTs, Device
tokens and user Bearer credentials do not authorize this stream. No credentials or
upstream URLs are returned; no user-supplied proxy URL is accepted. No audio fallback
exists. Selection is explicit; this backend phase does not switch a UI automatically.

## Verification and hardware gate

```bash
pnpm install --frozen-lockfile
pnpm check
MIMIX_TEST_DATABASE_URL=postgres://... pnpm --filter @mimix/api test:postgres
pnpm --filter @mimix/api exec playwright install --with-deps chromium
pnpm --filter @mimix/api exec node --test test/livekit/transport.test.js
```

The last command requires Linux Docker with host networking. It starts and deletes
its own isolated LiveKit 1.13.6 container with random credentials and ports, then
uses real Chromium WebRTC to publish robot camera/microphone and user microphone
for robot speaker, verifies received video frames/audio bytes, rejects forbidden
sources/tampered JWT, and observes provider disconnect. No physical hardware or
existing provider project is used.

Observed 2026-10-05 on this x86_64 host: synthetic loopback join **275 / 135 ms**;
first bidirectional camera/audio received **312 ms after publication began**.
This is one smoke sample, not a p95 or one-way/glass-to-glass measurement. Acceptance
targets for the hardware gate remain join <3 s, LAN one-way audio p95 <=200 ms,
video p95 <=300 ms. Do not infer those targets were met from this smoke.

LiveKit 1.13.6 publishes a Linux ARM64 image manifest
`sha256:4eeb7a7af9e133afee7d07fc48623373852a34ad709094345d1761c9b283dc1a`.
Artifact availability is not Jetson support. This host has no ARM64 hardware or
QEMU/binfmt registration. The isolated `docker run --platform linux/arm64` probe
using that digest stalled while downloading its layers and was stopped before
execution. No ARM64 code ran, and no ARM64/Jetson support is declared.

Run on the actual Jetson before promotion:

1. Record Jetson model, JetPack/L4T, kernel, aarch64, SDK/runtime versions, camera,
   microphone/speaker model and ALSA/V4L2 permissions. Build the Mimix image natively
   and execute health, migrations, API tests and the adapter smoke there.
2. Choose a supported robot SDK and publish real camera frames and microphone
   samples; route subscribed user audio to the approved speaker. Verify format,
   resampling, echo cancellation, gain and resource release after disconnect.
3. Measure timestamped join/first frame, audiovisual synchronization and one-way
   audio/video latency with synchronized clocks or a filmed/light/audio loopback.
   Collect at least 100 samples, p50/p95/max, CPU/RAM/temperature and sustained

4. Repeat wired LAN/Wi-Fi/TURN, camera unplug, muted/denied mic, revoked Clerk login,
   lost heartbeat, media expiry, network loss, provider failure and API restart.

5. Verify a real Cloud tenant's revocation cutoff and replay rejection. Separately
   demonstrate/document self-hosted cached-JWT replay; never mark it equivalent.

## Rollback

First stop new media traffic, close all active rooms through owner APIs and verify
no `active`/`closing` rows remain and no provider participants/rooms remain. Keep a
worker running while closing rows retry. If the provider is down, disable its
credentials/ingress and terminate rooms operationally before removing the worker.
Then set `MIMIX_MEDIA_PROVIDER=disabled` and roll back the application image. Keep
the additive table/migration in place; do not drop DeviceSession history. Turning
the flag off alone does not remotely terminate existing WebRTC rooms. Take a full
PostgreSQL backup (learning-only exports omit these operational sessions).
